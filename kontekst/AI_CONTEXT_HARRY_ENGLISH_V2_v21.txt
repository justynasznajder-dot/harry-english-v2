# HarryEnglish v2 — Kontekst projektu dla AI (v21)

Ten plik służy do przekazania kontekstu do nowego czatu AI. Wklej go na początku rozmowy.

**Źródło prawdy schematu bazy:** `prisma/schema.prisma` (introspekcja Neon + Prisma Migrate).  
Projekt używa **raw SQL przez `pg`** (`lib/db.ts`) — **bez Prisma Client** w runtime.  
Migracje: `prisma/migrations/` — patrz `prisma/MIGRATE.md`. Zapis w bazie wymaga `CONFIRM=1`.

- Next.js 16 App Router, React 19, TypeScript, Tailwind CSS v4
- PostgreSQL (Neon) — `pg`, bez ORM w runtime
- Auth: jose (JWT), cookie httpOnly 7 dni
- Maile: nodemailer (Zoho SMTP)

## 4. Model danych — zasady (szczegóły w schema.prisma)

**30 modeli** (introspekcja Neon). Kluczowe:

### users
- `role`: ADMIN | MANAGER | TEACHER | PARENT | CHILD
- `access_level`: PENDING | ACTIVE (tylko aktywacja konta rodzica)
- `school_id`: NULL tylko dla ADMIN
- Brak kolumny `account_type` (usunięte z kodu i bazy)

### children
- `access_level` — **źródło prawdy** steppera rodzica
- `enrollment_request_id` — opcjonalne powiązanie ze zgłoszeniem
- `confirmed` — TRUE po podpisie umowy
- Brak `preferred_location_id` (preferencja lokalizacji tylko w `enrollment_requests.preferred_location`)

### enrollment_requests
- Status ENUM `enrollment_status` w PostgreSQL
- Jedno zgłoszenie = jedno dziecko z formularza publicznego
- `proposed_group_id`, `proposed_at`, `accepted_at`, `rejected_at`
- `preferred_days` — kolumna istnieje, UI jej nie zbiera (zostaje NULL)

### contracts
- `status`: DRAFT → SENT → SIGNED
- `template_id`, `group_id`, `child_id` — NOT NULL w bazie
- `override_amount_monthly`, `override_amount_yearly`, `price_override`
- Załączniki: `attachment_1_html`, `attachment_2_html`, `include_attachment_2`

### renewal_proposals
- Historia propozycji grup w **odnowieniach** (osobno od enrollment)

**Usunięte:** tabela `enrollment_proposals`.

## 5. Przepływ zapisu (enrollment)

```
Formularz publiczny → enrollment_requests (NEW), bez konta rodzica
Manager: POST /api/admin/enrollment → tworzy/linkuje konto rodzica, dziecko w children,
         status PROPOSED, mail z propozycją grupy
Rodzic: PUT /api/enrollment/accept → ACCEPTED
Rodzic: POST /api/parent/contract/generate → umowa DRAFT/SENT
Rodzic: POST /api/enrollment/sign → SIGNED, users.access_level → ACTIVE
Alternatywa: PUT /api/enrollment/negotiate → NEGOTIATING → manager wysyła nową propozycję
```

**Multi-child:** jeden rodzic, wiele `enrollment_requests` / `children`. AdminPortal pokazuje status **per dziecko**. Batch mail: `POST /api/admin/enrollment/batch`.

**Synchronizacja:** `lib/enrollment-sync.ts` ustawia `children.access_level` i `users.access_level` po akcjach API.

## 6. API — role i uprawnienia

| Endpoint | Kto |
|----------|-----|
| `/api/admin/*` | ADMIN, MANAGER (`canAccessSchoolAdminApis`) |
| `/api/enrollment/*` | PARENT (JWT) |
| `/api/parent/contract/generate` | PARENT |
| `/api/auth/register` | Publiczny — tylko INSERT do `enrollment_requests` |
| `/api/user/me` | Zalogowany — zwraca `role`, `children[]` |

**Uwaga:** `POST /api/enrollment/sign` podpisuje **ostatni** kontrakt SENT rodzica (`LIMIT 1`) — ograniczenie przy równoległym podpisywaniu wielu dzieci.
